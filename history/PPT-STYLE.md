# PPT 讲解片风格 —— 可行性分析

针对 `article-to-ppt-video.md` 这份规格，评估把 `txt/20260816-2.md`（永住新规）
做成 PPT 演示风格讲解片的成本与风险。

**结论先说：可行，而且这篇稿子比现在的空镜风格更适合 PPT 风。**
主要成本在版式引擎（1–2 天），不在技术风险 —— 两个看起来最贵的环节实测都不需要。

分析时间：2026-08-16。现有风格（`landscape.mp4` / `portrait.mp4`）不受任何影响，见第五节。

---

## 一、这不是「换个字幕样式」

规格要求的四步里有三步跟现有管线是冲突的，不是叠加：

| | 现在（空镜解说风） | PPT 讲解风 |
|---|---|---|
| 配音 | **逐行合成**，时间轴天然精确到行 | **整条一次合成**，时间轴要靠词级时间戳还原 |
| 画面 | Pexels 空镜 + 运镜 + 冷调 LUT + 暗角 | **米白纯色底 `#FDF3E4`**，无素材、无运镜、无调色 |
| 文字 | 4 种 style（chip/sub/emph/emphKey） | **9 种版式**（hook/statement/timeline/compare/list/checklist/number/source/outro） |
| 竖版 | 同一条音轨换个字号重排 | **单独写一版解说词**（90 秒 / 400 字） |
| 主色 | 深底 + 正红 `#2222EE`(BGR) | 米白底 + `#C5381C` |

只有音轨那一层（混音、响度、自检）和 ffmpeg 骨架是可以原样复用的。

## 二、三个实测结论（都是原本以为要花大钱的地方）

### 1. 不需要 whisper —— 词级时间戳 TTS 自己就给

规格 Step 5 要求「跑强制对齐（whisper 词级时间戳），产出 srt 和画面切换点」。
这本来是最大的一块成本：新装 whisper.cpp / 模型文件 / Windows 编译。

**实测：`msedge-tts@2.0.7` 的 `wordBoundaryEnabled` 对中文可用**，
`toStream()` 会同时返回 `metadataStream`，逐词给出 `Offset` / `Duration`（单位 100 纳秒）。

用本篇 1309 字的解说词整条跑了一次：

```
整条文本长度: 1309 字
合成耗时:     23.1s / 音频 3.6MB
词事件数:     717
末词结束:     299.9s
词拼接 === 原文去标点  →  true（1171 字符完全一致）
```

**词拼接能精确还原原文**这一条是关键：它意味着「原文字符位置 → 时间」是一张可以精确
建出来的表，规格 Step 4 的 `anchor → start` 回填就是一次 `indexOf` 加累加查表，
不是模糊匹配。四个锚点实测：

| anchor | 字符位 | 回填的时间 |
|---|---|---|
| 而这里有一句话 | 456 | 116.0s |
| 接下来这段 | 598 | 150.8s |
| 那现在能做什么 | 883 | 225.5s |
| 制度在收紧 | 1139 | 291.1s |

whisper 这一整块可以从方案里划掉。

### 2. 整条合成没有长度墙

1309 字一次请求成功，23 秒返回。规格里那句「必须分时按语义段分（三四段），
接口交叉淡接 0.1 秒」的兜底方案用不上 —— 至少在 1300 字这个量级上不用。
（更长的稿子仍需实测，本篇没有触到上限。）

顺带一个数：整条合成 **299.9s**，逐行合成同一份稿子是 **291.9s**。
整条反而长 8 秒 —— 句间停顿由标点自然产生，比我们手写的 `pauseAfterMs` 更松。
规格要求「段落之间不留静音，必须停就 0.15–0.25 秒」，整条合成下 `pauseAfterMs` 这个旋钮是没有的。
**SSML `<break>` 已实测走不通**，改用「标点定停顿 + 事后裁静音」，见第七节。

### 3. 九种版式全都能在现有 ASS 引擎里做，不需要新渲染栈

原本以为要引入 HTML → PNG（headless 浏览器）或 SVG 渲染器。不用：

| 规格版式 | 现有能力 |
|---|---|
| `hook` 黑底大字 | **已经有了** —— 开场标题卡的四套版式之一 |
| `list` 要点逐条出现 | **已经有了** —— 就是 `stack` 机制（逐行淡入、不清屏、累加） |
| `statement` 单句结论 | `emphKey` 的变体 |
| `number` 大数字特写 | `hook` 放大字号 |
| `compare` 左右分栏 | 两个 `rect()` + 两列 `\pos` 文字 |
| `timeline` 逐点点亮 | 一条横线 + N 个方块，每个点位两个 event（灰/红）错开 start |
| `checklist` 逐项勾选 | `list` + 勾号字符，同样错开 start |
| `source` / `outro` | 多行小字，现成 |

底图从「Pexels 视频」换成「纯色」，在 ffmpeg 里是 `color=c=0xFDF3E4:s=1920x1080` 一个
lavfi source，**整个 `footage` 步骤直接不用跑**。

副作用是好的：没有 31 个片段归一化、没有 zoompan、没有 LUT、没有暗角，
渲染时间预计从 **10 分钟掉到 1–2 分钟**，文件大小掉到几 MB
（近静止画面对 x264 极其友好）。素材下载和 Pexels 配额也一并归零。

## 三、这篇稿子跟 PPT 风的匹配度：比空镜风高

这不是通用结论，是这一篇的特点。

**空镜风对这篇稿子是错配。** 政策、条文、数字类内容没有对应的实拍画面，
Pexels 只能给出泛化的办公室和笔记本电脑。今天出的那版里已经暴露了：
`narita airport arrival hall` 拿到曼谷机场、开场政府大楼疑似加拿大、
IT 段落是一段跟内容无关的 PHP 代码特写。画面没有承担信息，只是在填时间。

**而这篇稿子天生带着 PPT 结构：**

| 稿件里的东西 | 天然对应的版式 |
|---|---|
| 2026.04 / 2026.10 / 2027.04 三条时间线 | `timeline` —— 全片的核心，也是这篇最强的钩子 |
| 婚姻 3年+在留1年 → 5年+在留3年 | `compare` 左右分栏 |
| 收入 / 年金 / 配偶者特例 三条改动 | `list` 逐条 |
| 四种情况要留神 | `checklist` |
| 现在能做的三件事 | `checklist` |
| 400–500 万日元 / 30 年 / 70 分 80 分 | `number` |
| 收入要件追溯适用到今年 4 月以后的申请 | `statement` 单屏落点 |
| 时事 / 日经 / 入管厅 / e-Gov | `source` 片尾来源页 |

九种版式里有七种在这篇稿子里都有明确的落点。**这是少见的高匹配。**

字数上也对得上：规格说 4 分钟 ≈ 1000–1200 字，画面文字 150–200 字约 30 屏。
现有解说词 1309 字（4分52秒），砍到 ~1150 字就落在规格的默认档里。

顺带验证一条：规格的语速换算表写「中文讲解 4–5 字/秒」，
我们实测 Xiaoxiao `-5%` 是 **4.76 字/秒**，落在区间内。这张表可以直接用。

## 四、真正的风险，按大小排

1. **版式引擎的设计工作量（最大，但无技术风险）**
   9 种版式 × 横竖两套布局。`hook` 的四套版式已经证明路子通，但那是一个版式花了半天。
   9 个版式估 1–2 天。这是整个方案的主要成本。

2. **停顿控制：SSML 走不通，但退路更好（已验证，风险解除）**

   见第七节。结论：`<break>` 用不了，改用「标点选停顿 + 事后按词级时间戳裁静音」。

3. **锚点对齐在改稿后会漂（小，但要有护栏）**
   `anchor` 是解说词里的一句原文。稿子一改，锚点可能匹配不上或匹配到别处。
   必须加一条自检：所有 anchor 都能唯一命中，命中数 ≠ 屏数就报错。
   有了「拼接 === 原文」这个精确映射，这个自检很好写。

4. **竖版要单独写稿（不是技术问题，是内容工作量）**
   规格明确要求竖版另写 90 秒 / 400 字，不能删减主片。
   这等于每个选题要写两份稿。对当前这种一天两条的节奏，这是最实际的成本。

5. **超长稿件的合成上限（未知）**
   1309 字没问题，2000 字以上没测过。真要做长片再验。

## 五、隔离方案：怎么保证不碰到现有风格

**核心是加一个「风格」维度，而不是改现有常量。** 现有的 `ass.ts`、
`footage.ts`、`render.ts` 的滤镜链，一行都不动。

```
script.json 顶层加 "style": "doc" | "slide"（缺省 doc = 现有风格）

src/lib/ass.ts          ← 一行不动
src/lib/slides.ts       ← 新增，九种版式
src/steps/tts.ts        ← 加一个整条模式的分支（逐行模式原样保留为默认）
src/steps/footage.ts    ← slide 风格直接跳过，不进这个文件
src/steps/render.ts     ← 按风格选底图来源和滤镜链
src/smoke.ts            ← 必须加一条 slide 用例
```

三个具体的冲突点，处理方式：

- **`.env` 的 `VG_VOICE` / `VG_RATE` 是全局的。** 两种风格如果要用不同音色，
  得让 `script.json` 能覆盖它，或者加 `VG_SLIDE_VOICE`。**这是唯一会互相影响的地方，
  必须先解决。**
- **`ass.ts` 的 `BASE` / 颜色是模块级常量。** 不要改成可配 —— 新开 `slides.ts`
  用自己的一套，两边各自演化。重复几个常量比共享一套参数化的常量安全得多。
- **`render.ts` 的 LUT + 暗角是写死在 `vChain` 里的。** 按风格分叉即可，
  slide 风格的链是 `color 源 → subtitles`，比现在短得多。

**共享是安全且有益的那几块**：`util.ts`（ffmpeg / durationMs / lexicon）、
`buildAudioMix()`（音轨单独跑那个坑两种风格都会踩）、`assertAudioContinuous()`、
CRF 配置、项目目录结构。

**回归护栏**：`npx tsx src/smoke.ts` 现在只覆盖 doc 风格。加 slide 用例之前，
改 slide 的代码会不会静默弄坏 doc，没有任何东西拦得住。这条必须先做。

## 七、SSML break 注入 —— 实测结论

**`<break>` 在 Edge TTS 的免费端点上用不了。** 不是库的限制，是服务端拒绝。

库这一侧是通的：`_SSMLTemplate` 把输入**不转义**直接插进 SSML，
`toStream` 的文档注释还明写「Can include SSML elements」，另外还有
`rawToStream(requestSSML)` 可以完全接管 SSML 信封。但服务端不认。

每个变体单开一个进程测，排除连接复用的干扰：

| 变体 | 结果 |
|---|---|
| 纯文本 `toStream` | ✓ 71712 字节 |
| `rawToStream` + 手写信封（纯文本） | ✓ 71712 字节 —— **信封本身是被接受的** |
| `rawToStream` + 手写信封 + `<break time>` | ✗ 0 字节 |
| `<break time="600ms"/>` | ✗ 0 字节 |
| `<break time="600ms" />`（带空格） | ✗ 0 字节 |
| `<break time="600ms"></break>`（配对写法） | ✗ 0 字节 |
| `<mstts:silence type="Sentenceboundary" value="600ms"/>` | ✗ 0 字节 |
| `……` 省略号 | ✓ 有音频，但**字节数与纯文本完全相同**，等于被吞掉，一点停顿都没加 |

所有失败变体的报错都是同一句：
`Stream closed before the synthesis completed (no turn.end received)` ——
服务端收到停顿标签就直接掐断连接。`rawToStream` 那两行是关键对照：
同一个手写信封，不带 break 能出音频，带 break 就断，**证明是标签被拒，不是信封格式问题**。

（注意这个失败模式跟 `tts.ts` 里注释的「连接被掐掉后安静返回 0 字节」长得一模一样，
现有的重试逻辑会把它当成断线连试三次 —— 如果哪天真往稿子里混进了 SSML 标签，
表现会是「重试三次后报音色名可能非法」，很有迷惑性。）

### 退路：标点定停顿 + 事后裁静音

停顿控制并没有丢，只是换了个地方。同一次整条合成里量出来的自然停顿：

| 标点 | 实测停顿 |
|---|---|
| 逗号 `，` | **250 ms** |
| 分号 `；` | **289 ms** |
| 句号 `。` / 感叹号 `！` / 问号 `？` | **580–605 ms** |

两条推论：

1. **写稿阶段就有三档停顿可选**，而且逗号(250ms)和分号(289ms)正好落在规格
   要求的「段落间 ≤0.3 秒」区间里。句号是 600ms，正好是规格上限的两倍 ——
   规格那条要求的实际含义就是「段落之间不要用句号收尾停顿」。

2. **每个句号处都有 ~600ms 的真实静音**，所以整条音轨在句末是可以安全剪切的。
   要把某处 600ms 压到 250ms，就按词级时间戳定位到那段静音的中间，
   用 ffmpeg 剪掉 350ms —— 听感上完全无痕，因为剪的是纯静音，
   而且**语调是整条合成时就已经连贯的，剪静音不会引入语调重置**。

这条退路比 SSML `<break>` 还好：`<break>` 只能在合成前指定，
剪静音是在成品音轨上操作，可以反复调、可以按最终的分屏节奏来调，不用重新合成。

**代价**：多一步「按词级时间戳重排静音」的处理，估半天。
配套要改的是 `assertAudioContinuous()` —— 它现在见到 >100ms 的包空洞就报错，
而剪静音是有意为之的，得让它区分「时间戳空洞」和「有采样的静音」。

|---|---|---|

预估的「1–2 分钟」还高估了 —— 纯色底几乎没有帧间差异，x264 直接跑满。

### 第二节的三个预判，全部兑现

- 词级时间戳：826 个词，与解说词逐字对齐，锚点全部唯一命中 —— **没用 whisper**
- 整条合成：1484 字一次成功，没触到长度墙
- 九种版式：全部在 ASS 里做出来了，**没有引入任何新渲染栈**

### 新踩到的三个坑

1. **解说词不能出现 TTS 会归一化的写法。** 外文缩写和百分号会让词事件跟原文对不上，
   `tts-slide.ts` 直接抛错并指出第几个字开始不一致。本篇把 IT 从业者写成「在日工程师」、
   SES 写成「外包驻场」、N2 写成「日语二级」才通过。**屏幕上仍可以写 N2** ——
   画面文字不进 TTS。

2. **时间线版式要求解说按时间顺序讲。** 原稿是按重要性讲的（先明年四月、再十月、
   最后今年四月），节点会乱跳。改成时间序之后三个节点才能跟着解说依次点亮 ——
   **版式反过来约束了稿件结构**，这是这套风格跟空镜风最不一样的地方。

3. **竖版不能只按画幅宽度等比缩。** 1080/1920=0.5625 缩下来「占宽度的比例」不变，
   但手机上就是一堆蚂蚁。现在竖版额外乘 1.55。

### 跟规格的两处偏差

- **画面文字总量**：规格要 150–200 字，实际 783 字。规格这条跟它自己的
  「每屏正文不超过 20 字 × 约 30 屏」是矛盾的（那算出来上限是 600 字）。
  按可执行的那条算，实际**平均 17.8 字/屏**，符合。超过 20 字的 13 屏全是
  `compare` / `list` / `timeline` 这类天生多条目的版式。
- **片长**：规格默认 4 分钟 ≈ 1000–1200 字，实际 1329 字 / **5 分 41 秒**。
  净发声 201 ms/字，停顿占 65 秒（19%）。要压到 4 分钟得把解说词砍到约 1000 字，
  这是内容取舍，留给人定。

### 还没做的
